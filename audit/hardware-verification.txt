Cancellation follow-up

28da2ee fixes ordinary HTTP cancellation: HTTPClient owns a cloned WiFiClient,
so aborting the original disconnected client leaves the request running.
FeedHttpClient exposes its actual transport before connecting; the active guard
now tracks that clone for both protocols.
03e4a9a avoids WiFiClient::abort() on the main loop: the pinned core calls flush()
before TCP abort, potentially waiting for unacknowledged output. The shared socket
access helper calls ClientContext::abort() directly for HTTP and HTTPS, retaining
the suspended worker and TLS engine until their normal unwind.

The actual client regression reproduces a cloned HTTP connection, proves that
aborting the original fails to cancel it, and verifies direct cancellation of

Cancellation lifetime correction

9d8152e corrects a lifetime hazard introduced while tracking the cloned socket:
HTTPClient::end() can delete that clone before the active guard unwinds.
The guard now holds the still-live FeedHttpClient request object; cancellation
fetches its current transport each time and handles the null state after end().
The regression exercises cancellation after response cleanup, and all aggregate
checks pass. This avoids retaining a freed socket pointer across SDK yields.
